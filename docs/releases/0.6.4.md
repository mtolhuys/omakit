# 0.6.4

Tested plumbing, the marketplace's own checks, and a disposable Omarchy to test in.

A retry edit is never typed: it is the body `omakit submit` renders, and
`omakit watch` verifies afterwards that the issue says what `origin` says.

The incident this fixes is omacom/omarchy-plugin-marketplace#7787 on
2026-09-20 (UTC). 13:37 the issue was opened with the body from
`omakit submit` and validated. 16:12 the body was edited by hand to retry
after a push, still correct, validated again. 19:18 the body was edited
again by an agent following the validation-watch skill, which said "the
fix is to edit the issue body, do it yourself, outside this tool". The
agent retyped the whole body: the Repository URL became
`https://github.com/mtolhuijs/omacrunch` (a different, existing account,
no such repository) and the Maintainer notes were wiped. The `issues`
workflow run started 19:18:33; at 19:19:13 the marketplace labelled
`needs-fixes` with `repository-unreachable`, "The repository could not be
reached." 40 seconds. `omakit watch` reported the 404 as `unknown`, "HEAD
could not be read", the symptom without the cause; it had no verdict for a
failed validation; `submit` matched open issues by Repository URL, so the
issue with the typo was not "yours"; and the retry edit was the one step
the skills handed to the agent as free text.

## `watch` learns the subject

`omakit watch <issue-url> [<subject>]`. The subject is the plugin's
checkout (default: the current directory when it is a checkout with a
github.com origin and its `manifest.json` is the plugin the issue names;
another plugin's directory is reported as not compared, with its origin
and the reason, never as a mismatch) or its github.com URL. The issue's Repository URL is
compared with `origin`, normalised (https, no `.git`, no trailing slash,
owner and name case-insensitively). A mismatch is `wrong-repository`,
which wins over every other state: the summary names both URLs and the
action is to set the field to the origin and change nothing else. `--json`
carries `plugin.origin` and `plugin.repositoryMatches` (`null` without a
subject; `watch --all` has none). Exit 1, `error.code: "wrong-repository"`.

## `watch` reads a failed validation

The last `<!-- marketplace-validation -->` comment is passed or failed. A
failed one's reason is mapped to its code through the pinned
`scripts/submission-feedback.mjs` table (37 codes at the pin; a reason the
table does not know is verbatim, code `unrecognised`), and the labels
(`needs-fixes`, `security-needs-fixes`, `validated`,
`security-review-required`) are read from the pin. The marketplace edits
its comment in place, so the time of a refusal is `updated_at`. A refusal
newer than the last baseline marker is `refused`, with the marketplace's
own action as the arrow; a marker newer than the refusal is the state
again. On #7787 the marker said 16:12 and the refusal 19:19:13, and at
19:34:52 the corrected retry wrote a newer marker. `refused` ranks below
`wrong-repository` and above `unknown`; exit 1. `--all` counts refused rows
and exits 1 on one.

## `submit` finds your open issue even with a wrong URL

Open-issue discovery also matches a `[Plugin]:` submission whose title
carries the manifest's name or whose body names its id when its Repository
URL is another repository. The new check `submission.issue-repository-url`
(source `omakit`, blocking) holds that issue's URL to `origin`: "issue #N
says <url>, origin says <origin>", with the remedy "Edit issue #N and set
the Repository URL field to <origin>. Change nothing else." Skipped with
`--offline`, without a credential, and with no open submission issue by
the authenticated user for this plugin. M15, measured 2026-09-20 over all
651 open submission issues: 27 of the 646 with a readable URL name an owner
other than the issue's author, which is why the comparison is with
`origin` and never with the author's login.

## The retry edit stops being free text

`omakit submit ... --body-out <file>` writes the rendered body, and nothing
else, byte for byte the body in `--json`; a refusal writes nothing and says
so. The read-only test holds `cli.mjs` to that one local write, and no
source spawns `gh` to post it. The submit and validation-watch skills carry
one "Retry edit protocol": re-run `submit` with the original `--category`,
`--tags` and `--notes` plus `--body-out`; diff the file against the current
body (`gh issue view <url> --json body`) with only "### Maintainer notes"
allowed to differ; with the owner's explicit approval,
`gh issue edit <url> --body-file <file>`; then `omakit watch <url> <subject>`
and expect `current` within two minutes. Never retype the body, never write
the Repository URL by hand, never edit a `current` issue to bump it. The
suite holds the two protocol texts to each other.
