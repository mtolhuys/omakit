# 0.6.7

Tested plumbing, the marketplace's own checks, and a disposable Omarchy to test in.

`omakit doctor` no longer calls the pin behind when the marketplace changes
a file omakit never reads, and it says only what it measured when a file
omakit does read has moved. Measured on 2026-09-21
(`docs/MEASUREMENTS.md` M7): of the three marketplace commits that touched
`scripts/` since the first pin, one changed a file nothing omakit reads
reaches, and 0.6.6 moved the pin for it with no verdict changed.

## What omakit reads, named

`PIN_READS` in `tools/marketplace/pin.mjs` names the ten files omakit opens
under `scripts/` (seven imported, three read as text), and
`pinnedReadSet()` follows what the imported ones import, by regex over the
pinned text and never by loading a module: 16 of the 34 files there at
`b7b29654`. `tests/unit/pin.test.mjs` derives the ten from omakit's own
sources and pins the sixteen, so a new read is a visible diff. The one way
that closure could miss a file is an import form the regex does not
follow; the suite scans the executed read files for a dynamic `import()`,
a side-effect import, `require()` or `import.meta.resolve()` and fails by
file and line if one appears (0 of 13 at `b7b29654`), so a miss becomes a
test failure at the next pin bump, never a quiet `ok`.

## `pin.freshness`, graded by what a difference can do

The 16 files are compared by blob id through the git-trees API at the
exact commit (the `scripts/` tree is read only when its id moved); the
form directory stays a tree comparison; when the policy module's blob
moved, its text at HEAD is read once through the raw file host, its two
constants taken out the way the pin's identity reads them, and the text
dropped.

- `ok`: no read file moved. A `scripts/` change elsewhere is said as "in
  none of the 16 files omakit reads".
- `info`: the only moved files are ones omakit takes wording or a label
  out of (`WORDING_READS`: the baseline's rendered details, the failure
  table, one label from each approval script). What omakit prints may
  differ at HEAD; what it decides cannot. Nothing to do.
- `advice`: a file omakit executes or reads a rule from moved, whether or
  not `securityBaselineVersion` and `securityBaselineEnforcementMode`
  still read the same (a rule can change without its version), a read
  file is gone at HEAD, or the form moved. The action is `omakit upgrade`
  when a newer omakit is published, otherwise that the maintainer is
  notified; either way, every verdict is the pin's until then, and the
  marketplace's own run on your issue is the one that counts.

The two constants are printed beside every grade and soften none. Doctor
never asks you to open an issue: this repository's weekly pin-freshness
workflow opens the one there is, on `advice` or `info`, and its body names
the files, which of them a verdict can depend on, the constants at both
ends and doctor's line. Offline stays `unknown`. In `--json` the evidence
keeps `changedPaths`, `readLive` and `pinned` and adds `reads`, `moved`,
`verdictMoved`, `missing` and `policy.{pin,head}`.

The pin itself is unchanged at `b7b29654`: nothing omakit reads has moved
on the marketplace since 0.6.6.

Upgrade with:

```bash
omakit upgrade
```
