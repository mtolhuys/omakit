# 0.6.9

Tested plumbing, the marketplace's own checks, and a disposable Omarchy to test in.

`omakit lab` prepares the newest Omarchy release instead of the one it
was pinned to. Omarchy 4.0.4 was published on 2026-09-15, its ISO,
checksum and signature at iso.omarchy.org the same evening; on
2026-09-23 `omakit lab setup` still offered to download 4.0.3, because
the lab had been pinned to it on 2026-09-18 and nothing looked. Now every
lab action looks, and `setup` builds what it finds.

## The newest release, found each time

`omakit lab setup`, `inspect`, `prove` and `omakit doctor` read Omarchy's
release list (github.com/omacom/omarchy), sort it by version, and take
the newest release at or above 4.0.3 whose ISO, `.sha256` and `.sig` are
all published. A newer tag whose ISO is not up yet is passed over and
named; anything else that goes wrong (a timeout, a checksum that does not
read, a size that is not announced) stops the search with its reason,
rather than quietly settling on an older release. The search reads one
byte of each ISO, for its size, and no more. `--offline` skips it.

- `setup` builds the newest release, and removes the old base and the
  older downloads only after the new base has verified; until then a run
  uses what is there. With the release list unreadable it leaves a good
  base as it is and says so.
- A base of an older release is `outdated`: `prove` still runs it and says
  a newer release is out, `inspect` names it, and `doctor`'s new
  `lab.release` line gives the one action, `omakit lab setup`.
- A good base newer than the release found (a checksum being republished
  for a moment, an older ISO passed with `--from`) is `ahead` and kept:
  the lab never goes back a release on its own.
- `--from <iso>` must be the newest release when the list can be read;
  offline, it names its release by its file name and needs its `.sha256`
  and `.sig` beside it.

## What the trust rests on

The signature, as before: a file is the release only when its detached
signature verifies, in a throwaway keyring, against the Omarchy key omakit
ships at the pinned fingerprint `40DFB630FF42BCFFB047046CF0134EE680CAC571`.
The checksum now comes from the release itself instead of from omakit's
pin, which is safe because a substituted ISO with a matching substituted
checksum still fails the signature. The signer is read from the `.sig`
before the ISO is even asked for: a release signed only by another key
stops the search (`signer-changed`, with `omakit upgrade` as the action)
and is never replaced by an older release the old key signed.

## Proven on the reference host, 2026-09-23

`omakit lab setup` found 4.0.4 as the newest release, downloaded its
6,185,304,064 B in 4m 15.4s, verified its checksum and signature, built
the base with the pinned toolchain in 4m 28.5s (the installer's screens
unchanged from 4.0.3), read `omarchy 4.0.4-1` on kernel 7.2.5-3-omarchy in
the verification boot, and removed the 4.0.3 download after the promotion:
9m 50s from start to PREPARED. `omakit lab prove run` then proved the Run
block on the new guest, 19 of 19 scenarios in 2m 40.5s, its overlay
removed and the base unchanged, the record saying 4.0.4 is the newest
release. The setup ran on the change's first commit, before two independent
reviews; the Run suite, and the ISO re-verified with gpg, on the code that
ships. The figures are in `docs/MEASUREMENTS.md` (M14).

## Fixed on the way

- An interrupted `setup` left the toolchain's build VM running: the
  toolchain starts QEMU daemonized, and on the reference host one was
  still writing its disk eighteen minutes after the interrupt, invisible
  to `prune`. `setup` now stops every QEMU its build left, and also, once
  it holds the lab, any one a killed setup left; `inspect` shows it with
  its pid, and `prune` refuses to delete under it and names the `kill`.
- A blocked `setup` printed its blockers as `[object Object]`.
- A Ctrl-C while a request was in flight read as the network not
  answering; it is an interrupt now, and `prove` boots nothing after one.

The package packs to 372,357 bytes; its size ceiling, which exists to
catch an accidental tree rather than to hold the package small, is raised
from 358,400 to 409,600 bytes. The marketplace pin is unchanged at
`b7b29654`.

Upgrade with:

```bash
omakit upgrade
```
